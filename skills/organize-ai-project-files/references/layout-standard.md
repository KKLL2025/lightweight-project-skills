# 可选的项目布局模式

仅在项目级目录组织本身是任务或已观察到的障碍时读取本参考。这里的结构是可选模式，不是普通 Codex 执行、单仓库开发或日常文件放置的默认流程。

## 可选外层结构

对于新建的多仓库、混合资产或 AI 主导项目容器，如果统一入口确实能改善导航，可以采用简洁外层：

```text
project/
├── AGENTS.md 或 README.md             # 复用一个清晰入口
├── 01-ai-runtime/                    # 仅在有项目专属 AI 资源时
├── 02-project-control/               # 仅在有耐久项目资料时
└── 03-project-workspace/             # 产品、资产、数据或输出确需外层容器时
```

只创建实际需要的分支。三分区是兼容性示例，不是必须保持的名称、空目录清单或控制树。不要为了视觉统一创建索引、交接、验收、证据、历史或布局契约。

## 现有仓库优先兼容

当框架、包管理器、CI、构建或部署工具要求 `package.json`、`src/`、`apps/`、`Cargo.toml`、`go.mod` 等位于仓库根目录时，保留其原生结构。只在真实发现困难时增加最小导航入口或项目级资料区域，不要把整个仓库嵌套进外层模板。

成熟仓库、monorepo、第三方组件、数据集和其他稳定子系统应作为完整单元保留。普通源码、测试、配置和工程文档继续服从其自身约定。

## 按实际角色放置

- 复用现有合适位置，再考虑新增类别。
- 只有混放会明显影响导航、检索、所有权或维护时，才分开源码、耐久资料、生成输出、临时工作和 Agent 配置。
- 原始素材、用户数据和难以恢复的文件默认保持原位或进入明确的受保护位置；组织授权不等于删除授权。
- 文件夹名称只表达用途，不决定验收、发布或产品状态。正式发布和外部验收由项目已有机制负责，本 Skill 不创建或判定这些状态。

## 迁移保护按风险增加

简单、可逆且没有路径消费者的移动使用普通工程判断和最便宜的相关检查。

当大量引用路径会变化、难恢复资产参与迁移、外部系统依赖路径或回滚成本很高时，才按需使用显式映射、备份、盘点、完整性检查或更广验证。检查应覆盖实际受影响的路径和资产，不要扩展成无关的全项目审计。

## 可选工具

`assets/project-layout.json` 只是已有项目决定采用显式布局契约时的最小起点，不应复制到普通项目。`scripts/audit_layout.py` 只检查调用者明确声明的角色、文件或根目录允许项；它不评估发布状态，也不会在未提供 allowlist 时默认盘点整个根目录。

`scripts/tree_snapshot.py` 只用于确实需要内容保存证据的高风险迁移。创建快照时默认不哈希；只有需要内容级证明时才显式选择 `--hash-mode critical` 或 `--hash-mode all`。不要为普通归位、重命名或清理运行快照。
