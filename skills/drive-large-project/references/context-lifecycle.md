# Context and Document Lifecycle

Use this reference when resuming a project becomes difficult because current working information is scattered, duplicated, stale, or expensive to read. It is a guide for progressive recovery, not a recurring checklist.

## Core rule

Optimize the default read set, not merely the number of files. Split or archive material only when doing so makes the next resume materially easier.

## Read progressively

### Start with the smallest hot set

Read the repository rules and canonical project entrance first. Add the current Handoff, roadmap, or project plan only when the active work needs their roles. The hot set should answer what matters now, what is active or unfinished, and what the most useful next action is.

### Retrieve warm material selectively

Load the current requirements, design, task, architecture, migration, or recovery material selected by the active work. Inspect headings or search terms first when that is enough. Do not routinely replay project history, every control document, or the whole repository.

### Keep cold material out of the default path

Completed work, superseded plans, old logs, raw evidence, screenshots, and closed investigations should remain discoverable through the project's existing navigation or history without becoming mandatory resume input.

## Give changing state one owner

Prefer one primary maintained location for each changing concern:

- repository instructions own stable policy and hard constraints;
- the project map owns navigation and authority relationships;
- an existing roadmap or plan owns the practical project route when one is needed;
- the Handoff owns replaceable current working memory;
- a project-native acceptance or evidence record owns those facts only when the project actually uses one.

Other documents may link to these owners, but should not copy temporary status, completion counts, or competing next actions. Do not create any of these artifacts merely to satisfy this reference.

## Compact when real friction appears

Reduce or archive active material when a resume requires unnecessary reading, current facts are duplicated, the exact next action is hard to find, or closed history is mixed into current working memory. Prefer replacement, compression, and removal of obsolete material over indefinite appending. Do not use fixed line, character, or compaction-count thresholds as product requirements.

For closed work, retain only what future execution needs: the outcome, durable decision or invariant, useful evidence or revision pointer, and the condition that would require reopening it. Preserve exact requirements, user decisions, unresolved risks, legal or data-loss constraints, active interfaces, and audit evidence when they remain relevant.

## Re-anchor when reality requires it

Re-anchor when resuming across a Session or handoff, when the available summary is materially incomplete or conflicting, or when live state may have changed. Use current project evidence to repair stale summaries. Do not estimate or store hidden runtime compaction counts, and do not mechanically reload all skills, history, or control documents.

Re-anchoring is a consistency check, not an approval gate. If no material user decision is needed, repair the current state and continue with the smallest relevant context.

## Resume in two stages

1. Orient with the repository entrance, relevant rules, current Handoff or plan when present, and `git status` when worktree ownership matters.
2. Retrieve only the requirements, implementation area, dependencies, and checks needed for the selected bounded batch.

If documents conflict, prefer live state and the defined project-native owner, then repair the stale document instead of maintaining two live versions.

## Rotate proportionally

When moving closed material out of active context, identify the exact closed range, preserve it when it has audit value, update the current Handoff or map so the useful source remains discoverable, and run only the link or focused checks warranted by the change. A full archive, snapshot, hash, or repository audit is not required for ordinary context cleanup.
